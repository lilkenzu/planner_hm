# Планировщик встреч

Веб-страница для поиска удобного окна встречи для распределённой команды.
Организатор добавляет участников с их часовыми поясами и рабочими графиками —
инструмент строит недельную сетку доступности и показывает, когда и насколько
команде удобно созвониться.

Сделано в рамках домашнего задания курса (роль Project/Product, тема
«Планировщик встреч — окно, удобное всем»). Историю постановки задачи, все
вопросы и принятые решения см. в [`SPEC.md`](SPEC.md); ход работы с
ассистентом — в [`sessions/`](sessions/). Исходная инструкция задания
сохранена в [`HOMEWORK.md`](HOMEWORK.md).

## Запуск

Зависимостей нет — ничего устанавливать не нужно.

```bash
python3 -m http.server 8765
```

Открыть [http://localhost:8765](http://localhost:8765) в актуальном
Chrome/Firefox/Safari. Открывать нужно именно через локальный сервер, а не
двойным кликом по файлу — часть браузерных API так не заработает.

## Тесты

```bash
node tests/availability.test.js
```

Автотест функции расчёта доступности (`availability.js`): получасовой и
45-минутный сдвиг часового пояса (Катманду), переход через полночь местного
времени, обе границы рабочего часа, округление процента, вырожденный случай
с одним участником, полная неделя на трёх участниках с проверкой всех
возможных значений процента. Тест ничего не пишет на диск и не ходит в сеть.

## Что сделано

- Форма участника: имя, город (автодополнение по списку часовых поясов IANA,
  которые знает браузер), рабочие часы, рабочие дни недели. Добавление,
  редактирование, удаление — без перезагрузки страницы.
- Сетка на ближайшие 7 календарных дней (реальные даты, не абстрактная
  неделя) с шагом 30 минут: строка на участника, время — в его собственном
  локальном времени, заливка ячейки — доля участников, доступных в этот
  момент.
- Клик по любой ячейке — список недоступных участников, причина (нерабочий
  день / до начала рабочего дня / после его окончания) и разница во времени.
- Если ни один слот недели не набрал 100% участников — баннер с лучшим
  найденным слотом (день, время, X из N) и подсветка соответствующей ячейки.
- Обработка ошибок: нераспознанный город не добавляет участника и показывает
  ошибку у поля, не ломая форму.
- Пустое состояние: без участников видна только форма; удаление последнего
  участника возвращает в пустое состояние.
- Часовые пояса и переводы времени — только через встроенные `Intl`/`Date`;
  без единой сторонней библиотеки, без сборки, без сети (проверено вкладкой
  Network браузера при реальной работе со страницей — запросов, кроме
  загрузки самой страницы, нет).

## Что не сделано (сознательно, см. `SPEC.md` → «Чего точно не делаем»)

- Нет сохранения состояния между визитами: ни `localStorage`, ни сервер.
  Каждый заход — с чистого листа. Это явная нецель, а не недоделка.
- Нет интеграции с календарями и отправки приглашений — инструмент только
  считает и показывает.
- Нет выбора диапазона дат вручную — всегда ближайшие 7 дней от текущего
  момента.
- Инструмент не выбирает «лучший» слот автоматически и не бронирует его —
  решение всегда остаётся за человеком.

## Допущения

Полный список с обоснованием — в `SPEC.md` → «Допущения». Коротко: шаг сетки
30 минут, диапазон — 7 календарных дней от текущего момента (а не абстрактная
неделя — иначе нельзя корректно показать переход на летнее время), минимум
1 участник для показа сетки, порог «нет полного совпадения» — отсутствие хотя
бы одного 100%-слота, округление процента до целого, полуоткрытый интервал
рабочего часа `[начало, конец)`.

## Ограничения

- Часовой пояс участника выбирается из стандартного списка IANA — если у
  браузера в `Intl.supportedValuesOf('timeZone')` его нет, добавить нельзя.
- Для поясов с нецелым смещением (например, Катманду, UTC+5:45) отметки в
  сетке приходятся на «:15»/«:45», а не на «:00»/«:30» — это не баг, а
  неустранимое свойство самого смещения.
- Проверено на актуальных версиях Chrome/Firefox/Safari; более старые
  браузеры без поддержки `Intl.supportedValuesOf` не поддерживаются
  намеренно (см. `AGENTS.md`).

## Проверка и доказательства

- Автотест: `node tests/availability.test.js` — граничные случаи расчёта
  доступности, вывод команды.
- Ручная проверка обоих пограничных сценариев из задания — Москва/Лондон на
  переходе летнего времени и Катманду (+5:45) — через реальное приложение,
  подробности и цифры в `sessions/session-1.md`, шаг 7.
- Вкладка Network браузера пуста при добавлении/редактировании/удалении
  участников и клике по сетке — нет ни одного запроса, кроме загрузки самой
  страницы.
- `grep` по коду — нет `import`/`require`/`<script src="http...">`, нет
  упоминаний CDN, нет `package.json`/конфигов сборщиков, нет `fetch`/`XHR`/
  `WebSocket`, нет `localStorage`/`sessionStorage`/`indexedDB`/cookies.

## Наивный прогон и сравнение

Наивный прогон (один короткий промпт без спеки и правил) сделан отдельно,
результат — в [`naive-run/`](naive-run/). Независимый аудит (чистая сессия,
без истории разработки ни одного из вариантов) — в
[`sessions/audit.md`](sessions/audit.md).

**Главный вывод аудита**: наивный вариант на пограничном случае, ради которого
и затевалась спека — переход на летнее время, — тихо показывает неверные
данные без предупреждения. Он строит сетку от wall-time к UTC и не
обрабатывает «дыру» перехода (29 марта 2026, `Europe/London`, 01:00–02:00 не
существует): слоты «01:00» и «01:30» в его сетке — точные дубликаты «00:00»
и «00:30» под другими подписями, с неверными данными о доступности. Итоговый
вариант строит сетку в обратном направлении — от реальных UTC-моментов к
локальному времени участника, — и на этой же проверке ошибки не даёт (см.
`sessions/session-1.md`, шаг 7, и `sessions/audit.md`).

Остальные отличия — не баги, а расхождения в объёме и дизайне: наивный вариант
предлагает свободный выбор недели и более развёрнутый список «лучших окон»
при отсутствии полного совпадения; итоговый — жёстко держит рамки спеки
(7 дней от сегодня, один лучший слот) и добавляет то, чего у наивного нет
вовсе: автотесты и журнал разработки. Полная таблица — в `sessions/audit.md`.
